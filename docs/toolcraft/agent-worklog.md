# Implementation Worklog

This file records product decisions and the evidence behind them. Keep it short, factual, and current. Update it after schema, renderer, timeline, layer, export, performance, or acceptance decisions.

## Status

Mode: product

ASCII 3D Studio is a Toolcraft configurator that reproduces the dragonfly.xyz live-ASCII-3D technique (analyzed from the running site's WebGL2 bundle: a scene rendered to a texture, quantized into a character grid, luminance mapped to a font-glyph atlas, plus a pointer heat-trail feedback buffer) as an original, general-purpose, editable tool.

### Iteration 20 -- Made SVG extrude depth a live, user-adjustable control

- Request: "now i want to be able to modulate the strength of the extrusion" -- follow-up to Iteration 19, which shipped SVG extrusion at a single fixed ratio (`SVG_EXTRUDE_DEPTH_RATIO = 0.08`, a module constant with no schema control), flagged in that iteration's own Risks section as a likely next ask ("a future iteration could expose this as a schema slider if a fixed default proves wrong for enough real uploads").
- Task type: promote an existing internal constant to a live `AsciiEffectParams` field plus a schema slider control, following the same shape as every other numeric live control in this app (e.g. `tiltX`, `greyscaleIntensity`).
- Decision: added `svgExtrudeDepth: number` to `AsciiEffectParams` (default `0.08`, matching the old constant exactly, so existing SVG uploads render identically until the user touches the new slider). `buildSvgGroup()` now reads `this.params.svgExtrudeDepth` (still clamped to a small positive floor, `MIN_SVG_EXTRUDE_DEPTH_RATIO = 0.005`, so the slider can't drive it to a degenerate zero-thickness `ExtrudeGeometry`) instead of the removed module constant. Because the extrude depth is baked into the geometry once at load time (not read per-frame the way a shader uniform would be), `setParams()` needed a new reload trigger: it now also captures the previous `svgExtrudeDepth` before merging, and calls `setModel(this.params.model)` again when the new value differs from the previous one AND the currently-displayed model is actually an SVG (`this.params.model.kind === "url" && this.params.model.format === "svg"`) -- gated exactly like that, rather than "whenever `next.svgExtrudeDepth !== undefined`", because `AsciiCanvas.tsx` calls `setParams` with the full params object on every sync, so an unguarded check would reload on every single render regardless of whether the value actually changed or an SVG is even showing. Added a new "Depth" slider (`model.svgExtrudeDepth`, range 0.01-0.4, step 0.01, default 0.08) -- first attempted adding it directly into the existing "Custom Model" section alongside the FileDrop, but a throwaway vitest check that printed the *resolved* schema (not the authored one) showed the fileDrop `source` control had been silently dropped entirely once a sibling control existed in the same section -- a real, previously-undocumented runtime constraint (a fileDrop apparently must be the sole control in its section). Fixed by giving the slider its own section, titled "Model Extrusion" (distinct from "Custom Model" so two identical section headers don't stack visually) with the identical `visibleWhen: { equals: "custom", target: "model.shape" }`, so the two sections always show/hide together even though they're structurally separate. Its description states up front that it's SVG-only and ignored for every other format, since the control stays visible even when the current upload is a GLTF/OBJ/FBX/STL (Toolcraft's schema has no way to gate visibility on the *uploaded file's own format*, only on `model.shape`, which only distinguishes "custom" from the built-in presets).
- Alternatives rejected: gating the slider's visibility on the uploaded file actually being an SVG (via some custom check of the `model.source` media asset's filename) -- rejected as unnecessary complexity for a control that already states its own scope in its description text, matching the existing precedent of the STL material caveat living in prose (`source`'s own description) rather than conditional UI. Making the reload check `next.svgExtrudeDepth !== undefined` alone (matching how `next.model` and `next.distance` are checked elsewhere in `setParams`) -- rejected once traced through `AsciiCanvas.tsx`'s actual call pattern (full params object every render, not a diffed partial), which would have made this reload every single param sync; added the explicit previous-value comparison specifically because this field's calling convention differs from a true "only present when it changed" partial update.
- State/output mapping: `model.svgExtrudeDepth` -> `AsciiCanvas.tsx` reads it via `useToolcraftValue` (default `0.08`, matching the schema default) -> included in every `setParams()` call and its effect dependency array -> `AsciiEffect.setParams` detects an actual change while an SVG is showing -> re-runs `setModel` -> `buildSvgGroup()` re-extrudes at the new ratio -> same `frameObject()`/`replaceMesh()` convergence every format already uses. Also threaded into `build-code-export.ts`'s `readState()` (`Number(values["model.svgExtrudeDepth"] ?? 0.08)`), which `formatParamsLiteral`'s generic `Object.entries` loop already picks up automatically -- no export-builder changes needed beyond that one read.
- Files changed: `src/app/ascii-engine/ascii-effect.ts` (`AsciiEffectParams.svgExtrudeDepth`, `DEFAULT_ASCII_PARAMS`, removed `SVG_EXTRUDE_DEPTH_RATIO` in favor of the new param, added `MIN_SVG_EXTRUDE_DEPTH_RATIO` floor, `buildSvgGroup()` reads the param, `setParams()` reload logic), `src/app/app-schema.ts` (new "Model Extrusion" section with the `svgExtrudeDepth` slider, split from "Custom Model" for the fileDrop-standalone reason above), `src/app/AsciiCanvas.tsx` (reads the value, threads it through `setParams`), `src/app/export/build-code-export.ts` (`readState()` reads it, README "Custom models" section documents it), `src/app/app-acceptance-data.ts` (new control-section-inventory entry for "Model Extrusion" / `model.svgExtrudeDepth`, alongside the existing "Custom Model" / `model.source` entry), this worklog.
- Verification: `npx tsc --noEmit` -- 0 errors. `npx vite build --outDir /tmp/...` -- succeeds. `npx vitest run src` -- same pass/fail counts as every prior iteration (219/226, same 7 pre-existing gaps -- confirmed the pre-existing `app-performance.scenarios.test.ts` gap, which already failed on `ascii.granularity` before this change, now also flags `model.svgExtrudeDepth` as an additional performance-sensitive control missing from `workloadTargets`; this is the same standing, undressed gap as `granularity`/every other slider in this app, not a new category of failure -- no new failing test *files*). Along the way, the fileDrop-standalone-section constraint above was caught precisely because `app-schema.test.ts`'s existing "exposes a single Shape selector... and a Custom Model upload gated by it" test failed after the first (wrong) attempt -- `customModelSection?.controls.source` came back `undefined` -- which is what prompted printing the actual resolved schema and finding the fileDrop control had been dropped; after splitting into two sections, this test (and the full suite) is back to the identical 219/226 baseline. Repeated the real-bundle export check (generated a real export via `buildCodeExportZip`, unzipped, ran `esbuild usage-example.ts --bundle --external:three` against the flat folder) -- bundled clean, and confirmed the generated `usage-example.ts` literal includes `svgExtrudeDepth: 0.08,` (and a second run with `0.22` to confirm the value actually threads through, not just a hardcoded default) alongside the other ascii params.
- Skipped checks: no real browser in this sandbox to visually confirm the slider actually changes the rendered thickness in real time, or that dragging it repeatedly (rapid-fire `setParams` calls, each re-running the full SVG parse + extrude) doesn't introduce visible jank -- the extrude/parse work is not currently debounced, so a fast slider drag will re-run `SVGLoader.loadAsync` + `ExtrudeGeometry` on every intermediate value. ### Iteration 19 -- SVG upload, extruded into a 3D model

- Request: "Can we have the option to upload SVG and Extrude them? And then exporting use them as obg or whatever, must work tho" -- SVG as a sixth (now fifth-format-family) upload option, extruded into 3D geometry, with an explicit reliability bar given the Iteration 17 regression scare.
- Task type: new model-format support in the shared engine, following the exact same additive pattern as Iteration 18's FBX/STL work (widen `AsciiModelSource`, add a `setModel` branch, update the two duplicated format-detector functions, widen the schema `accept` string).
- Decision: considered two architectures before implementing. (A) Intercept the upload at `fileDrop` time, convert SVG -> extruded mesh -> re-export as an actual `.obj` via three's `OBJExporter`, and store *that* through the existing `model.source`/`mediaAssets` pipeline, so `AsciiEffect` and `build-code-export.ts` would need zero SVG-specific code at all. (B) Treat `"svg"` as a sixth `AsciiModelSource.format`, exactly like FBX/STL, with the SVG-to-3D conversion living inside `AsciiEffect.setModel()` itself. Chose (B): `build-code-export.ts` already bundles `ascii-effect.ts` into every export wholesale (verified working end-to-end for FBX/STL in Iteration 18, including the real-bundle esbuild check that catches cross-file import breakage) -- so any loader logic added inside that one file ships automatically with no export-builder changes beyond the format-detector string, the same low-risk shape as the STL precedent (STL also needed a bespoke non-`loadAsync`-returns-Object3D wrapping step). (A) would have required confirming whether Toolcraft's `fileDrop` control supports intercepting/transforming an upload before it's stored -- an unconfirmed, more invasive integration point -- for no benefit over (B) given the export architecture already in place.
- Implementation: added `SVGLoader` (`three/examples/jsm/loaders/SVGLoader.js`) alongside the other loaders. New private `buildSvgGroup(url)`: loads and parses the SVG, skips any path with `fill: "none"` (stroke-only outlines -- this engine extrudes filled regions, not stroked lines), calls `SVGLoader.createShapes(path)` per remaining path (handles holes automatically, e.g. a donut/letter "O"), and for each resulting `THREE.Shape` builds a `THREE.ExtrudeGeometry` with a small bevel. Extrude depth is computed as a ratio (`SVG_EXTRUDE_DEPTH_RATIO = 0.08`) of the SVG's own bounding width/height (measured from all shape points before extruding) rather than a fixed unit count, since SVG source coordinate scales vary wildly (a 24x24 icon grid vs. a 1000-unit illustration) and the result is re-normalized by the existing `frameObject()` step regardless -- what matters is the *ratio* of thickness to footprint, not absolute units. Each mesh is colored from that path's own SVG fill (`path.color`, defaulting to SVG's own default fill of black when unspecified) via `buildDefaultMaterial()`, which gained an optional `color` parameter (previously hardcoded to white, used by presets and STL) so multi-color logos/icons keep their per-shape colors after extrusion, matching how GLTF/OBJ/FBX already preserve embedded materials. All shapes are collected into one `THREE.Group`, y-flipped once (`group.scale.y = -1`, since SVG's Y axis points down and three.js's points up -- otherwise every extruded shape renders vertically mirrored), then returned to `setModel()` which threads it through the same `frameObject()` centering/scaling every other format already uses. Throws a clear error (caught by `setModel`'s existing try/catch, which already keeps the previous model on screen rather than silently reverting) if an SVG has no fillable paths at all (e.g. a pure line-art/stroke-only file).
- Alternatives rejected: architecture (A) above (extrude-then-export-to-OBJ at upload time) -- reasoned through in detail but not implemented; rejected once (B) was confirmed to require materially less new surface area for equal reliability, given the export builder already ships `ascii-effect.ts` verbatim. ### Iteration 17 (hotfix) -- Iteration 16's forceContextLoss() broke the live studio under React StrictMode

- Request: user reported the live studio now shows a runtime error screen, "Cannot read properties of null (reading 'precision')," describing it as having "broke everything." Urgent regression, addressed immediately.
- Root cause: Iteration 16 added `this.renderer.forceContextLoss()` to `AsciiEffect.dispose()`, unconditionally. `AsciiCanvas.tsx`'s mount effect creates one `AsciiEffect` per `canvasRef.current` and disposes it in the effect's cleanup function -- and React 18 `StrictMode` (development only) deliberately double-invokes every effect on mount: mount -> cleanup -> mount again, synchronously, reusing the exact same `<canvas>` DOM node. So the sequence became: first `AsciiEffect` constructed -> StrictMode immediately cleans it up -> `dispose()` calls `forceContextLoss()` on that canvas's WebGL context -> StrictMode mounts a second `AsciiEffect` on the SAME canvas element -> its `new THREE.WebGLRenderer({ canvas, ... })` inherits that already-lost context (a `<canvas>` can only ever have one real WebGL context; once lost, a fresh `getContext()` call on it does not create a new usable one) -> three's internal capability probing (which reads shader precision info from the context) receives `null` back and throws exactly the reported error. Confirmed by rereading `AsciiCanvas.tsx`'s mount effect: `effect.dispose()` is called with no arguments on every cleanup, so this reproduces on every StrictMode double-invoke, i.e. constantly in development.
- Decision: made `forceContextLoss` opt-in instead of automatic. `dispose(options: { forceContextLoss?: boolean } = {})` now only calls `renderer.forceContextLoss()` when explicitly requested; the default (`false`) matches pre-Iteration-16 behavior exactly. `AsciiCanvas.tsx`'s `effect.dispose()` call site is unchanged (still no arguments), so it now safely omits the forced context loss and the live studio is restored. The capability itself is preserved for the use case Iteration 16 added it for (the dev team's landing page with several long-lived, never-remounted asset instances) -- it's just no longer the default, since only the caller can know whether a given canvas element is being discarded for good or might get a fresh effect mounted on it again (React re-render, hot reload, or any other reuse pattern). Documented this tradeoff directly on the method (a long doc comment explaining exactly why the default is off, including the StrictMode failure mode by name) so a future pass doesn't reintroduce the same regression. Updated the export's generated `usage-example.ts` cleanup comment and README API listing to show the option and the same warning.
- Alternatives rejected: keeping `forceContextLoss()` unconditional and instead telling the user to disable `StrictMode` -- rejected, since `StrictMode` is a legitimate, common React development default that this engine has no business requiring callers to turn off, and the same failure mode could just as easily hit hot-module-reload or any other legitimate same-canvas remount, not just `StrictMode` specifically. Removing `forceContextLoss()` entirely -- rejected, since the dev team's original report and measurement (2 canvases/166 draw-calls -> 0/0) was real and worth keeping available; making it opt-in gets both.
- Files changed: `src/app/ascii-engine/ascii-effect.ts` (`dispose()` signature + doc comment), `src/app/export/build-code-export.ts` (usage-example cleanup comment, README API surface), this worklog.
- Verification: `npx tsc --noEmit` -- 0 errors. `npx vite build --outDir /tmp/...` -- succeeds. `npx vitest run src` -- 219/226, same 7 pre-existing gaps, no new failures. Confirmed by direct inspection that `AsciiCanvas.tsx`'s only `dispose()` call site passes no arguments, so it now resolves to the safe (non-context-losing) default -- this is the concrete fix for the reported crash. ### Iteration 14 -- Six engine correctness fixes from an external code review of the exported bundle

- Request: the user's team reviewed the framework-agnostic export ("The engine is solid... but we hit six issues worth fixing in the tool so future exports are correct for everyone... - Task type: Six independent correctness bugs in the shared rendering engine (`ascii-engine/ascii-effect.ts` and `ascii-engine/shaders.ts`) plus the generated export docs, no schema/control changes.
- Decision, per issue:
  1. **Wheel-zoom hijacking page scroll.** `OrbitControls.enableZoom` was left at its library default of `true` even though `enablePan` was explicitly set `false` and the README already documented zoom as intentionally unbound. `OrbitControls` calls `preventDefault()` on wheel events, so any visitor scrolling a page with the effect embedded, whose cursor happened to be over the canvas, had page scroll silently hijacked. Fix: `this.controls.enableZoom = false;` next to `enablePan`. Zoom stays available via the documented `distance` param.
  2. **Auto-rotate speed tied to monitor refresh rate.** `renderFrame` called `controls.update()` with no argument, so `OrbitControls` fell back to a fixed per-frame rotation step that assumes 60fps (per three's own docs, real-time-independent auto-rotate requires passing `deltaTime` in seconds) -- `lastFrameTime` was already being tracked every frame but never actually read anywhere, so this looks like an unfinished wire-up rather than a deliberate choice. Fix: `start()`'s rAF tick now computes `deltaSeconds` from the real gap between frame timestamps (clamped to 0.1s via a new `MAX_FRAME_DELTA_SECONDS` constant, so a tab regaining focus after being backgrounded doesn't jump rotation by the whole elapsed gap) and passes it into `renderFrame(deltaSeconds)`, which forwards it to `controls.update(deltaSeconds)`. `renderFrame` defaults to a new `ASSUMED_FRAME_SECONDS = 1/60` constant when called with no argument (i.e. `renderOnce()`'s single ad-hoc frame, used for PNG export), preserving its exact prior behavior. At a true 60fps `deltaSeconds` is already `1/60`, so on the frame rate this app was authored against, math confirmed bit-for-bit identical to the old fixed-step formula (`OrbitControls._getAutoRotationAngle`: `(2*PI/60*speed)*deltaTime` at `deltaTime = 1/60` equals the old `2*PI/60/60*speed`).
  3. **Transparent output not premultiplied.** `shaders.ts`'s composite pass used a single `mix(uBackground, shaded, coverage)` + `alpha = coverage` for both the `includeBackground` on/off cases, but WebGL canvases are premultiplied-alpha by default (color channels must already be multiplied by their own alpha). In the `includeBackground: false` branch this left a `uBackground * (1 - coverage)` term in the output, which shows up as an additive veil of the background color across the whole canvas (worst exactly where the render is most transparent) plus a dark fringe on every anti-aliased glyph edge, since those edges compose against `uBackground` instead of whatever's actually behind the canvas on the page. Fix: split into two branches -- `includeBackground: true` keeps the `mix()` (alpha is always 1, so premultiplying is a no-op and nothing changes for that path) and `includeBackground: false` now outputs `vec4(shaded * coverage, coverage)`, properly premultiplied.
  4. **Renderer requested `alpha: false` while relying on an alpha channel.** `new THREE.WebGLRenderer({ alpha: false, ... })` contradicted the `includeBackground: false` path's actual dependency on the canvas having a real alpha channel; it happened to still work because the installed three version (0.169.0) reports `alpha: true` from the context regardless of the request, but that's the renderer disagreeing with its own configuration, not a guarantee -- a future three release that starts honoring the flag would silently turn every transparent export opaque black. Fix: `alpha: true`.
  5. **Pointer trail decay tied to frame rate.** Same root cause as #2: `uDecay` (0.9) was applied once per rendered *frame* in `trailFragmentShader`, not once per unit *time*, so the heat trail fades proportionally faster on higher-refresh-rate displays. Low priority per the review (this app runs with `mouseTrail: false` by default), fixed anyway since the export ships the same shader. Fix: added a `uDeltaTime` uniform to the trail material (updated every frame alongside the same `deltaSeconds` from fix #2) and changed the shader to `float decay = pow(uDecay, uDeltaTime * 60.0); float previous = texture2D(uPrevTrail, vUv).r * decay;` -- time-normalized against the same 60fps baseline everything else in this app assumes.
  6. **`getParams()` returned the live internal params object.** A caller reading the returned object could mutate engine state directly, desyncing `this.params` from what's actually been uploaded to the GPU uniforms/`OrbitControls` (only `setParams` is supposed to be able to do that). Fix: `getParams()` now returns `{ ...this.params }`, a shallow copy.
  - **Docs.** The generated export's `README.md` and `usage-example.ts` comment already described the *intended* zoom behavior correctly (unbound wheel, `distance` param instead) -- the actual docs bug was that this text described behavior the shipped code didn't yet enforce (bug #1). Fix #3 is shader-only. ### Iteration 5 -- Brightness leaking into background; base tilt controls

- Request: "The brightness should not influence the bg, i want to make just the object characters more visible, not everything. Add the option do add default xyz angles, if i want the object to rotate little angled like a key for example."
- Task type: Broken/misbehaving control fix (shader logic) + new schema controls + renderer feature.
- User-visible result: Raising Brightness now only lifts the object's own glyphs; empty background cells no longer sprout characters or a faint fill as Brightness increases. A new "Orientation" section (Tilt X/Y/Z, -180..180 degrees) sets a fixed base angle for the object, independent of auto-rotate/drag, so it can spin around a tilted axis (e.g. a key tumbling at an angle) instead of always upright.
- Source/reference checked: User's bug report; re-read the exact fragment shader math (`asciiFragmentShader` in `shaders.ts`) and `AsciiEffect`'s render-target clear configuration to find the actual mechanism.
- Docs/contracts read: `decision-contract.md` (broken control route), `component-rules.md` Vector Ownership (`direct-authored` classification for a stable, user-set pose parameter).
- Contract rules applied: root-cause-first fix -- traced the actual pixel math instead of guessing at a tuning constant.
- Decision: **(a) Brightness leak.** Root cause: `uBrightness` was added to `lum` unconditionally for every screen cell, including cells with no object at all (`lum = clamp(toLuma(scene.rgb) + trail*0.65 + uBrightness, 0, 1)`). Because the renderer cleared the scene render target to opaque black (`setClearColor(0x000000, 1)`), empty background pixels already had `luma = 0` before any brightness was added -- indistinguishable, in RGB terms, from a genuinely dark part of the object. Once `uBrightness` pushed a background cell's `lum` high enough to cross the character ramp's first threshold (or, with "Fill cells" on, past its `step(0.02, lum)` gate), the background started rendering visible glyphs/fill even though nothing was there. Fixed at the source instead of papering over it with a threshold hack: changed the scene render target's clear alpha from 1 to 0, so its alpha channel now doubles as a free "is there an object here" mask (opaque materials always write alpha 1 wherever they actually draw, regardless of the clear value) -- then gated the brightness term by that mask in the shader: `uBrightness * objectMask` instead of a bare `uBrightness`. Background cells (`objectMask == 0`) are now completely unaffected by the Brightness control; only pixels where the object was actually rendered are lifted. The other two render passes (pointer trail, final composite) fully overwrite their targets every frame with a full-screen quad regardless of clear value, so changing the shared clear alpha doesn't affect them. **(b) Base tilt.** Now that auto-rotate and drag-rotate are both camera moves (`OrbitControls` orbiting the origin, since Iteration 3), the object's own `modelGroup.rotation` was sitting completely unused at identity -- a clean, conflict-free place to apply a static user-set pose. Added `tiltX`/`tiltY`/`tiltZ` (degrees, -180..180) applied via `THREE.MathUtils.degToRad` directly to `modelGroup.rotation`, recomputed once at construction and again whenever any tilt param changes. Because it's `modelGroup`-level and camera-orbit is separate, tilt and rotation compose exactly as expected: the object holds its tilted pose while auto-rotate/drag orbits the camera around it, producing the "key on a ring" tumble the user described.
- Alternatives rejected: Clamping/tuning the brightness range instead of fixing the underlying cause -- rejected because it would only mask the symptom at certain values and reintroduce visible background bleed at higher Brightness settings. Using a luminance threshold (e.g. "treat lum < 0.01 as background") instead of a real alpha-channel object mask -- rejected because it would misclassify genuinely dark regions of the object itself as "background" and exempt them from Brightness too, which is not what was asked. A `vector` control for tilt -- rejected because the built-in `vector` control is explicitly two-axis (X/Y pad); a true 3-axis rotation has no matching built-in, so three plain sliders (already the established pattern for `motion.rotateSpeed` etc. in this app) is the correct built-in-first choice per `core/control-selection.md`.
- State/output mapping: `appearance.brightness` -> `uBrightness` uniform, now multiplied by `scene.a` (object mask) inside the fragment shader rather than applied unconditionally. `model.tiltX/Y/Z` -> `AsciiEffect.applyTilt()` -> `modelGroup.rotation.set(...)`, called from both the constructor and `setParams` whenever any tilt value changes.
- Files changed: `src/app/ascii-engine/shaders.ts` (object-mask-gated brightness term), `src/app/ascii-engine/ascii-effect.ts` (clear alpha 0, `tiltX/Y/Z` params + `applyTilt()`), `src/app/AsciiCanvas.tsx` (reads and forwards the three new targets), `src/app/app-schema.ts` (new "Orientation" section), `src/app/export/build-code-export.ts` (includes tilt in the exported defaults), `src/app/app-acceptance-data.ts`, `src/app/app-schema.test.ts`, this worklog.
